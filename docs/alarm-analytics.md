# 报警统计分析（ISA-18.2 / EEMUA 191）

菜单“报警分析”（`/alarm-analytics`）是报警性能评审仪表盘：KPI、坏分子、洪水、合理化建议、下钻明细与导出；报表中心可用“报警 KPI”列定时生成签名归档的报警 KPI 报表。报警管理本身（状态、暂挂、抑制、通知）见 `alarm-management.md`。

## 统计口径

- **统计对象**：开始时刻落在 `[from, to)` 的报警（半开区间）。长期驻留、陈旧、抑制时长另外纳入 **from 之前开始、from 时仍活动** 的报警。
- **需报警（annunciated）**：不含暂挂、条件抑制、抖动标记的报警。报警率、洪水、优先级分布、确认/恢复时间只算需报警；坏分子排行算全部报警。
- **报警源**：同一报警规则视为同一条报警（无规则时按测点 / 设备 / 网关 / 消息）。
- **观察点 asOf** = min(窗口结束, 当前时刻)。长期驻留和陈旧都按 asOf 判断。

| 指标 | 定义 | 参考目标（EEMUA 191） |
|---|---|---|
| 每操作员每 10 分钟 / 每小时 / 每天 | 需报警数 ÷ 时长 ÷ 操作员岗位数 | 平均每 10 分钟 ≤1 可接受、≤2 可管理；每小时 ≤6；每天 ≤144 |
| 评级 | 按每 10 分钟平均值：≤可接受 → 可接受；≤可管理 → 可管理；≤洪水结束阈值 → 可能过高；≤洪水起始阈值 → 很可能过高；更高 → 不可接受 | — |
| 10 分钟桶分布 | 与纪元对齐的 10 分钟桶，按每操作员报警数归入 可接受 / 可管理 / 偏高 / 洪水 四档的占比 | — |
| 峰值 10 分钟 | 单个桶内需报警数的最大值及其时刻 | ≤10 |
| 洪水 | 某桶每操作员报警数 > 起始阈值（默认 10）时进入洪水；之后只要桶内 ≥ 结束阈值（默认 5）就延续，低于结束阈值时退出（滞回）。可跨零点、跨月 | 洪水时间占比 <1% |
| 洪水时间占比 | 洪水区间与窗口的重叠时长 ÷ 窗口时长 | <1% |
| 首发报警（first-out） | 洪水区间内第一条需报警；同时列出前 10 名主要报警，以及区间内全部报警 ID（最多 500 条，可下钻） | — |
| 确认 / 恢复时间 | 需报警的 AckTs−StartTs、EndTs−StartTs 的平均值和中位数 | — |
| 长期驻留（standing） | 在 asOf 仍活动、且已持续 ≥ `standingHours`（默认 24h）。另给出“窗口内曾达到长期驻留”的数量 | 尽量为 0 |
| 陈旧（stale） | 在 asOf 仍活动、未确认、且已持续 ≥ `staleHours`（默认 24h） | 0 |
| 暂挂 | 与窗口重叠的暂挂次数，以及截到 [from, asOf] 内的暂挂时长；按规则分别统计 | — |
| 抑制时长 | 带抑制标记的报警，其活动区间截到窗口内的时长 | — |
| 抖动（chattering） | 同一报警源在 `chatterWindowSec`（默认 60 秒，含边界）内触发 ≥ `chatterCount`（默认 3）次，算一次片段；片段之间不重叠 | — |
| 瞬时（fleeting） | 持续 ≤ `fleetingSec`（默认 10 秒）即恢复，且恢复前没人确认 | — |
| 关联 / 重复（consequential） | 对每条报警，统计其后 `consequentialWindowSec`（默认 5 秒）内出现的其他报警源，每个源只算一次，累加到这一对。比例 = 同现次数 ÷ 两者中较少的报警次数（封顶 1）。同现 ≥ `consequentialMinCount`（5），且比例 ≥ `consequentialMinRatio`（0.8）才列出 | — |
| 优先级分布 | 需报警中 低（提示）/ 中（警告）/ 高（严重）的占比 | 约 80 / 15 / 5 |
| Top N 坏分子 | 按报警源计数，附占比、累计占比（帕累托）、抖动片段数和瞬时次数 | 前 10 名通常占 >50%，应优先治理 |

## 合理化建议（只给建议，从不自动修改）

每条建议都列出依据（证据数值）、规则的当前配置（触发延时、恢复延时、恢复死区、等级），以及可以给出的建议值。修改规则要到报警规则页面，按正常流程审批。

| 类型 | 触发条件 | 建议 |
|---|---|---|
| 抖动 | 有抖动片段 | 加大恢复死区；恢复延时建议值 = 恢复后再次触发间隔的 P90（1～300 秒），只在大于当前值时给出 |
| 瞬时报警 | 瞬时 ≥3 次，且占该源 ≥30% | 触发延时建议值 = 瞬时持续时间 P90 + 1 秒（1～300 秒），只在大于当前值时给出 |
| 长期驻留 | 当前长期驻留 | 核实报警是否仍有效，考虑按工况抑制或调整设定值 |
| 频繁报警 | 平均每天超过 `frequentPerDay`（默认 10），且不是抖动源 | 复核设定值和报警必要性 |
| 优先级复核 | 高优先级报警出现频繁，或高优先级占比超过目标的 1.5 倍 | 复核优先级 |
| 关联报警 | 满足关联判定 | 对后发报警考虑按工况抑制（条件测点）或合并 |

## 预聚合、回补与保留

- 表 `AlarmRollup` 按（粒度、桶、报警源、等级）汇总开始于该桶的报警：小时桶为 UTC 整点，日桶为 `ShiftTimeZone` 的本地零点。字段包括计数、需报警、暂挂、抑制、抖动、瞬时、确认数与确认时间合计、恢复数与恢复时间合计。区域不写进表，查询时按报警源的测点或设备推导，所以测点改区域后无需重算。
- 后台任务 `AlarmRollupService` 每 `AlarmRollupIntervalSec`（默认 300 秒）汇总到最近的整点，备机不运行：
  - 首次回补 `AlarmRollupBackfillDays`（默认 400）天，从最早的报警起算。超出小时保留期的日子只生成日行。
  - 每轮重算最近 `AlarmRollupRecomputeHours`（默认 48）小时，用来吸收迟到的确认和恢复。
  - 小时行保留 `AlarmRollupHourlyRetentionDays`（默认 90）天，日行保留 `AlarmRollupDailyRetentionDays`（默认 1095）天。原始报警表不受影响。
- `POST /api/alarm-analytics/rollups/rebuild {days}` 手动重算最近 N 天，需全局配置权限并写审计。修改“瞬时秒数”阈值会自动安排重算小时保留期内的数据。`GET /api/alarm-analytics/rollups` 查看水位、上次运行时间、错误和行数。
- **查询策略**：区间 ≤ `AlarmAnalyticsRawMaxDays`（默认 31 天）时全部现算原始明细。更长时（最长 366 天）：
  - 最近 31 天做明细分析，包括峰值、洪水、抖动、瞬时清单、关联、中位数和合理化建议。
  - 更早的部分用预聚合，并入计数、比例、均值、优先级分布、Top N 和瞬时总数。中间的完整本地日用日行，首尾不足一天的部分用小时行。
  - 预聚合尚未覆盖的尾段用原始数据现算。界面会提示明细从哪一刻开始。
  - 原始明细行数超过 `AlarmAnalyticsMaxRows`（默认 50 万）时，只取最近的部分并提示。
- 索引：新增 `AlarmEvent(RuleId, StartTs)` 和 `AlarmEvent(EndTs, StartTs)`（已有 `StartTs`、`TagId+StartTs`）；`AlarmRollup(Granularity, BucketTs, Source, Level)` 唯一。
- 本机粗测（SQLite，40 万条报警、500 个报警源、跨 120 天）：

| 操作 | 耗时 |
|---|---|
| 首次回补 | 约 16 秒 |
| 增量汇总 | 约 0.3 秒 |
| 分析 1 天 | 约 0.4 秒 |
| 分析 31 天 | 约 0.8 秒 |
| 分析 120 天 | 约 1.1 秒 |
| 趋势 120 天 | 约 0.6 秒 |

## 阈值配置

`GET/PUT /api/alarm-analytics/thresholds`。数据存在单行表 `AlarmAnalyticsConfig`（JSON + 版本号）。没保存过时使用默认值，部分默认值来自 `Scada:AlarmFloodThreshold`、`AlarmChatterCount`、`AlarmChatterWindowSec`、`AlarmStandingHours`。修改需全局配置权限：

- 写差分审计（`修改报警分析阈值`）；
- 版本号冲突返回 409；
- 保存时校验参数，例如洪水结束阈值须 ≤ 起始阈值，优先级目标须合计 100%；
- 库中的 JSON 被手工改坏时回退到默认值。

字段如下：

| 字段 | 含义 |
|---|---|
| `operatorPositions` | 操作员岗位数，0 表示按确认人数 |
| `acceptablePer10Min`、`manageablePer10Min` | 可接受、可管理报警率 |
| `floodStartPer10Min`、`floodEndPer10Min` | 洪水起始、结束阈值 |
| `chatterCount`、`chatterWindowSec` | 抖动判定 |
| `fleetingSec` | 瞬时报警秒数 |
| `standingHours`、`staleHours` | 长期驻留、陈旧小时数 |
| `consequential*` | 关联报警判定 |
| `frequentPerDay` | 频繁报警阈值 |
| `target*Percent` | 优先级目标比例 |
| `topN` | 默认 Top N |

## 接口与权限

| 接口 | 说明 | 权限 |
|---|---|---|
| `GET /api/alarm-analytics?from&to&areaId&levels&rules&top` | KPI、坏分子、洪水、10 分钟报警率、合理化建议、生效阈值、明细起点 | 查看；结果只含有权查看区域的报警；指定无权区域返回 404 |
| `GET /api/alarm-analytics/trend` | 小时趋势（≤2 天）或本地日趋势，按等级分组 | 同上 |
| `GET /api/alarm-analytics/events?source&kind&ids&limit` | 下钻明细；kind 可取 annunciated / fleeting / chattering / shelved / suppressed | 同上 |
| `GET /api/alarm-analytics/export?format=xlsx\|pdf` | 导出 Excel（每节一个工作表）或 PDF；按请求语言输出；写操作日志 | 同上 |
| `GET /api/alarm-analytics/thresholds`、`/rollups` | 读取阈值、预聚合状态 | 查看 |
| `PUT /api/alarm-analytics/thresholds`、`POST /rollups/rebuild` | 修改阈值、手动重算 | 全局配置 |

`levels` 为等级编号列表（0 提示、1 警告、2 严重），`rules` 为规则 ID 列表，区间最长 366 天。

## 仪表盘

- 筛选条件：时间（含 24 小时 / 7 天 / 30 天快捷选项）、区域、等级、规则、Top N。
- 卡片：按 EEMUA 目标着色。
- 图表：
  - 10 分钟报警率：洪水区间着色，并画出洪水阈值线和可接受线；
  - 等级堆叠趋势；
  - 优先级实际占比与目标（内圈）对比；
  - Top N 帕累托图。
- **下钻**：点击柱子、扇区、帕累托柱，或任一表格行，都会打开对应时段、等级或报警源的明细；点击洪水行打开该洪水内的全部报警。
- 页签：最频繁、抖动、瞬时、关联、洪水（首发报警与主要报警）、长期驻留与陈旧、暂挂、合理化建议。合理化建议页签会注明“仅供参考、不会自动修改”。
- 导出 Excel / PDF；有全局配置权限的用户可以打开“分析阈值”对话框，对话框中显示默认值，可一键恢复默认。
- 全部文案都有中英两套，键在 `alarmAnalytics.*` 下；后端导出文案在 `messages.en-US.json`。

## 报表中心：报警 KPI 报表

- 新列类型 `AlarmKpi`，`output` 取以下指标键之一：
  - 计数与报警率：`total`、`annunciated`、`perOperator10Min`、`perOperatorHour`、`peak10Min`；
  - 洪水：`floodPercent`、`floods`；
  - 确认与恢复时间：`avgAckSec`、`medianAckSec`、`avgClearSec`、`medianClearSec`；
  - 坏分子与驻留：`chatterEpisodes`、`fleeting`、`standing`、`stale`；
  - 暂挂、抑制与优先级：`shelvedHours`、`suppressedHours`、`highPercent`。
- 统计范围是模板所在区域，口径与仪表盘一致。逐行（小时或日）分别计算，汇总行按整个周期重算，不是逐行相加。
- 模板编辑器的“报警 KPI 预设列”按钮一键填入 10 个常用指标，再选周期和定时即可得到报警 KPI 日报、班报或月报。
- 归档、版本、SHA256、CMS 签名、审核批准和邮件投递都与其他报表相同（见 `reports.md`、`report-signing.md`）。

## 已知限制

- 抖动和瞬时的判定以报警事件为准，看不到被触发延时过滤掉的原始越限。规则配置的抖动标记（实时）与本页的抖动片段（事后统计）口径相近，但不完全一致。
- 长区间的早期部分来自预聚合：没有峰值、洪水、中位数、抖动片段，也没有关联分析。预聚合只覆盖回补范围，默认 400 天，更早的报警需要手动重算才会计入。
- 每轮只重算最近 48 小时：报警开始 48 小时以后才确认或恢复的，预聚合中的确认、恢复统计要等手动重算才会更新。明细窗口内不受影响。
- 关联分析只看先后出现的同现，不判断因果；每条报警最多向后看 200 条。
- 优先级按三档等级映射（提示 / 警告 / 严重 → 低 / 中 / 高），不支持自定义优先级矩阵。
- 阈值为全局配置，不能按区域设置；也不随工程包导出。
- 设备离线、网关等无规则报警不能暂挂，所以暂挂统计只按规则计。

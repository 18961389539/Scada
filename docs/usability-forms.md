# 表单与配置易用性

针对高频组态页（测点、设备、报警规则；计算测点做了轻量加固）统一了校验提示、新建默认值和批量操作。

## 校验

- 对话框内使用 Element Plus 字段规则；必填未填时保存按钮禁用。
- 服务端 400 的 `message` 会尽量映射到对应字段旁（无字段级 errors 时按文案启发式）；无法映射时显示在表单顶部。
- 计算测点仍保留「试算 → 再保存」；名称为空或表达式为空时不可保存。

## 默认值（新建）

| 页面 | 默认 |
| --- | --- |
| 测点 | Float、变化存档、周期 600s、只读；区域随协议切换 |
| 设备 | Modbus TCP `127.0.0.1:502`、站号 1、轮询 1000ms、超时 3000ms、启用 |
| 报警规则 | 高限、警告、触发延时 3s、恢复延时 0、启用 |
| 计算测点 | 启用、周期 1000ms、输入有效期 15s、变化存档 |

对话框顶部有简短说明。测点 / 报警规则 / 设备支持「复制」（名称追加 `_副本`；复制设备默认停用以免误连）。

## 批量操作

无独立批量 API：前端顺序调用单条接口，进度条提示，部分失败时弹窗列出明细（不静默失败）。

| 页面 | 批量能力 |
| --- | --- |
| 测点 | 多选物理测点；批量改存档方式；批量删除 |
| 报警规则 | 多选；批量启用 / 停用；批量删除 |
| 设备 | 多选；批量启用 / 停用；批量删除（有测点的设备会失败并列出） |

共享实现：`web/src/composables/batchRunner.ts`、`formErrors.ts`。

## 报警页（运行）

报警页操作多数不可撤销或与现场安全相关，因此以「先确认、再执行、结果可见」为原则。

- **二次确认**：「确认可见」（一键确认所有可见报警）、「声光消音」（会停掉现场声光）、「解除暂挂」（规则的新报警重新通知）都会先弹出确认框并显示影响条数/对象；确认可见在无未确认报警时直接提示，不弹框。
- **批量确认**：实时页勾选多条 → 「批量确认 (N)」。逐条调用单条接口，工具栏显示进度，结束后有失败明细（部分失败不静默）；已确认的行自动跳过，避免整批因个别 400 失败。
- **声光消音**：逐个面板调用，失败时列出面板名与原因（此前是串行直调，首个失败即中断且无明细）。
- **暂挂校验**：原因必填且保存按钮禁用；服务端 400 尽量落到原因字段旁；时长旁提示「默认暂挂 60 分钟，到期自动解除」；提交期间按钮 loading，防重复提交。
- **筛选**：实时页支持等级（严重/警告/提示）+ 关键词；关键词与历史页共用同一过滤，便于按内容收敛。
- **历史快捷范围**：最近 1 小时 / 8 小时 / 24 小时 / 7 天，选中即查询，仍可用日期区间覆盖。

测试：`web/tests/alarm-usability.spec.ts`。

## 实时页

现场读数的两个痛点是「找不出哪个点坏了」和「数值一直在跳没法看」，因此围绕这两点改进：

- **质量筛选**：全部质量 / 仅异常 / 仅正常。异常包含 `Bad`、`CommFailure`、`Uncertain`，未采集到值的测点也计为异常。
- **异常计数与高亮**：标题栏在存在异常时显示「异常 N」；异常行整行着色（坏值红、不确定黄），不必逐个扫数值颜色。
- **搜索覆盖设备名**：关键词同时匹配测点名、描述与设备名，现场通常按设备找点。
- **暂停刷新**：暂停期间丢弃推送、表格冻结便于读数；恢复时补拉一次快照，冻结期间的变化不会丢。
- **写值参考**：写值对话框给出「量程 min ~ max 单位」与「当前值」，避免凭记忆改数，也便于判断写入是否真的变化。

测试：`web/tests/realtime-usability.spec.ts`。

## 趋势页

查询前和查询后都缺少反馈，是这一页最影响判断的地方：

- **空状态区分两种情况**：未选测点提示「请先选择测点」，已查询但无数据提示「该时间段没有历史数据」，不再是一整块空白（原先只能靠猜）。
- **预置范围有选中态**：当前生效的 1h/6h/24h/7d/30d 按钮高亮；手动改日期后取消高亮。
- **已选计数与一键清空**：多选折叠时也能看到「已选 N」，并可一键清空。
- **自定义范围选完即查**：与预置按钮行为一致，不再需要额外点一次「查询」。
- **数据点统计**：工具栏显示「N 点 / M 测点」，便于判断返回量是否符合预期。
- **自动刷新**：默认关闭，开启后每 30 秒重查（仅在有测点且无查询进行中时触发）。

测试：`web/tests/trends-usability.spec.ts`。

## 顶栏

- **实时连接状态可见**：断线或重连中时，标题旁出现红色状态标签并说明「数据可能不是最新，恢复后会自动补齐」。此前页面看着一切正常、数据其实已停止更新，只有进入实时页才知道。
- **声音开关移动端可用**：原先移动端直接隐藏了开关（手机浏览器同样会播报警音）。现在两端都有，移动端只是不显示「开/关」文字；悬停/长按给出「浏览器报警提示音」说明。
- **健康标签有内容**：悬停显示「设备 N/M 在线 · 积压 N · 磁盘剩余 N GB」，不再只有「系统正常」四个字。
- **报警铃铛有说明**：悬停显示未确认条数，点击跳转报警页。

测试：`web/tests/topbar-usability.spec.ts`。

## 总览

登录首屏的目标是「一眼看出哪里有问题，并且能直接点过去」：

- **统计卡片可点击**：设备在线 → 实时监视、未确认报警 → 报警页、配置测点 → 实时监视、历史存储 → 系统管理。此前卡片是纯展示，看到「未确认报警 3」还得自己找入口。
- **权限感知**：只跳转当前用户可见的页面；无权时卡片保持纯展示（无光标、无 tabindex），不会给出点不动的错觉。
- **键盘可达**：可点击卡片带 `role="button"` 与 `tabindex="0"`，聚焦后回车即可跳转。
- **异常阈值视觉**：左侧色条 + 数字着色。设备部分离线为黄、全部离线为红；总线积压为黄；磁盘剩余低于 5 GB 为红。
- **设备卡片显示离线台数**：有设备离线时副标题直接写「N 台离线」，而不是固定的「采集任务运行状态」。

测试：`web/tests/overview-usability.spec.ts`。

## 控制页

安全操作原本都已有确认（批准填备注、切模式说明影响、启停顺控列出步骤），缺的是**审批时的判断依据**和**待办可见性**：

- **有效期可见**：双人复核请求带 `expiresTs`，此前前端从未展示。现在列表有「有效期」列，显示剩余时间，60 秒内标红，过期显示「已过期」，每秒刷新。
- **审批弹窗带摘要**：弹窗会遮住表格，此前只问「批准备注」，等于盲批。现在 message 里带上「请求内容 · 申请人 · 申请时间 · 剩余有效期」。
- **待审批自动刷新**：此前只有顺控运行状态每秒刷新，待审批列表必须手动点「刷新」才知道有新请求。现在在「待审批」页签下每 5 秒自动拉取。

注意：自己不能批自己的请求（`mine` 由后端按 `RequestedByUserId` 判定），测试里需另建操作员账号复核。

测试：`web/tests/control-usability.spec.ts`。

## 报警分析

- **无数据不再空白**：此前 `v-if` 只判 `kpi && report`，而后端在无数据时仍返回全 0 的 kpi 对象，页面会显示一排 0 卡片；查询失败时则除工具栏外整页空白。现在按 `kpi.total > 0` 判断，无数据时显示「该时间范围内没有报警数据」，未查询时显示「选择时间范围与筛选条件后点击查询」。
- **评级阈值可查**：EEMUA 191 的「每操作员每 10 分钟报警数」卡片悬停显示阈值依据（≤可接受值 / ≤可处理值 / 超出则过于苛刻），阈值取自报告返回的 `thresholds`，不是硬编码。
- **修复等级筛选失效**：`AlarmLevel.Info = 0`，而后端用 `ParseIds` 解析 `levels` 参数，其中 `.Where(x => x > 0)` 会把 0 过滤掉——于是「只筛选提示级」被当成「不筛选」，静默返回全部数据。已改为专用解析（保留 0）。此前等级筛选器对「提示」级**从来不生效**。

测试：`web/tests/analytics-usability.spec.ts`。

## 网关管理

这一页本身已经比较完整（URL 驱动的详情弹窗、基于服务端时间的状态推算、busy 防并发、轮换密钥的确认文案明确写了「旧密钥立即失效、仅显示一次」、释放会话要求先勾选「网关已停止」），因此只做三处打磨：

- **危险操作区隔**：下拉菜单里「释放会话」加了分隔线与红色，避免与「启停 / 轮换密钥」混在一起顺手点到。
- **最后刷新带相对时间**：显示「最后刷新 18:30:12 · 12 秒前」。绝对时间用于对照日志，相对时间用于判断数据是否新鲜（由每秒 tick 驱动）。
- **详情设备清单可筛选**：网关下设备较多时可就地按名称/协议过滤，不必翻页找。

测试：`web/tests/gateways-usability.spec.ts`。

## 设计一致性修正（2026-10-25 审查）

按「同类 0 值陷阱 / 配置阈值是否真的被消费 / 危险操作保护是否一致」三类扫了一遍全站，修掉两处：

- **OEE 主数据删除无确认、失败无提示**：产线/产品/班次/停机原因/停机记录共 5 个删除按钮都是 `type="danger"` 却一点就删，且删除函数没有 try/catch——删除失败（通常是被历史数据引用）会抛未捕获异常，用户只看到行没消失。现在统一走 `confirmRemove()`：先确认（文案提示「不可恢复、被引用会失败」），失败时给出具体原因。保存函数同样缺错误处理，但至少有「对话框不关闭」的反馈，暂未改动。
- **报警分析的小时/日阈值硬编码**：`perOperatorHour > 12 / > 6`、`perOperatorDay > 288 / > 144` 是写死的，而 10 分钟阈值来自可配置的 `thresholds`。改阈值配置后只有「每 10 分钟」那张卡片会变色。现在改为按 `acceptablePer10Min × 6`、`manageablePer10Min × 6`（日则 ×144）推导。

**审查后确认无问题的部分**（避免重复排查）：

- `EndpointHelpers.ParseIds` 的其余用法（History / Realtime / Report / ExternalRest）传的都是测点 ID，过滤 `<= 0` 是正确的；只有报警分析的等级参数会取到 0。
- `AnnunciatorView`（2 处）与 `NotificationsView`（6 处）的删除用 `el-popconfirm`，已有确认。
- OEE 看板的 `pctClass(kpi.oee, th.targetOee)` 正确使用配置阈值，与报警分析页的硬编码形成对照。

测试：`web/tests/oee-design-fix.spec.ts`。

## 设计一致性修正（第二轮审查）

按「表单失败是否可见 / 显示语义是否唯一 / 权限模型与界面是否对齐」三类扫全站，修掉四处：

- **OEE 表单三缺**：7 个对话框零校验规则、保存函数无 try/catch、按钮无 loading。后果是三件事同时发生——空名称/重名点保存「按钮像没反应」、请求可以连点两次、服务端 400/409 全部无人展示。现在统一走 `saveWith()`：`el-form` 规则前置校验 → `saving` 防重复 → 失败时把服务端文案经 `mapServerFieldError` 落到具体字段，对话框保留。
- **并发修订冲突（409）完全静默**：服务端 `产线已被他人修改` 等 409 返回 `{message, revision}`，前端原先既不刷新也不提示，用户以为保存成功，继续在过期数据上编辑。现在 409 单独提示「请关闭对话框重新打开后再修改」。
- **加载失败静默**：`OeeView.load()` 是 `try { ... } finally` 没有 `catch`——分析接口出错时用户只看到转圈消失，页面停在旧数据上；`refreshMeta()`、`exportAs()` 同理（导出走裸 `fetch`，网络错误直接抛未捕获）。均已补 catch 与 `errorMessage`。
- **产品/停机原因缺区域归属**：服务端按 `AreaId` 判权（留空=全局，需全局 `Configure`），但两个对话框都没有区域字段，新建时恒为 `null`——只有区域级 `Configure` 权限的用户看得到「新增」按钮，点了必被拒。现在补区域选择，默认值按当前用户权限推导（全局权限→留空，否则默认其可配置区域）。
- **趋势图例与导出歧义**：选择器显示「设备 / 测点」，图例与 CSV 导出只用测点名。不同设备常同名（如「温度 1」），多选后无法对应。现统一带设备名。
- **时间格式混用**：OEE 停机表、通知记录、OPC 证书用 `toLocaleString()`（随语言变成 `2026/10/25 19:02:51` 或 `10/25/2026, 7:02:51 PM`），与全站 `formatTime` 的 `YYYY-MM-DD HH:mm:ss` 不一致。已统一。
- **看板无数据无解释**：`plannedMs` 与 `total` 同时为 0 时 A/P/Q/OEE 全是「—」，看不出是配置问题还是故障，现在给出说明并指向班次配置与计数测点绑定。

**审查后确认无问题的部分**（避免重复排查）：

- 默认时间范围各页不同（趋势 1h、报警/分析/OEE 24h）是刻意区分：趋势看「最近」，其余看「当日」，不统一。
- `|| 0` 仅 `ObjectTemplatesView` 的批量数量用到，`Math.max(0, count || 0)` 语义正确。
- 其余 `catch { return }` 均为 `ElMessageBox` 取消分支，不是吞异常。

测试：`web/tests/oee-design-fix.spec.ts`（新增第二个用例：空名称拦截、重名 400 落字段、产品区域选择）。

## 权限口径一致性（第三轮审查）

服务端判权分三种口径：**全局权限**（`HasGlobal`）、**区域权限**（`Has(perm, areaId)`）、**任意区域**（`HasAny`）。界面上若用更宽的口径判断，用户就会看到按钮、填完表单、最后被 403。本轮按「服务端要什么 / 界面按什么显示」逐条比对：

| 位置 | 服务端要求 | 原界面 | 现在 |
|------|-----------|--------|------|
| 测点 Excel 导入（`POST /tags/import`） | 全局 `Configure`（可覆盖任意设备的测点） | **无任何门槛**，View 级用户也能看到上传控件 | `hasGlobal(Configure)` 才显示 |
| OEE 阈值（`PUT /oee/thresholds`） | 全局 `Configure` | `hasAny(Configure)` | `hasGlobal(Configure)` |
| OEE 主数据行内编辑/删除 | 行所属区域 `Configure`；`areaId` 为空则需全局 | 全部按 `hasAny` | `canEditArea(row.areaId)`：有区域按区域，空区域按全局 |
| 声光面板 编辑/删除/消音/试验 | 面板区域 `Configure` / `AckAlarm`；全局面板的配置需全局 | 全部按 `hasAny` | `canConfigurePanel` / `canAckPanel` 按 `row.areaId` 区分 |
| 声光面板 新建默认区域 | 全局面板需全局 `Configure` | 恒为「全局」 | 有全局权限→「全局」，否则落到其可配置区域 |
| `/config/external-api`、`/ops` 路由 | `AccessPolicies.GlobalSystem` | 守卫按 `hasAny(Configure)` 放行，导航却按 System 隐藏——直接输 URL 能进到必 403 的页面 | 新增 `systemOnly` 列表，与导航目录同口径 |

顺带确认：`NotificationsView` 的通知渠道、`ScreensView` 的草稿、`ProjectView` 的全局段，服务端要全局权限的地方界面已经用 `hasGlobal`，无需改动；测点新增/修改/删除服务端按设备区域判权（`RequireTagsAsync` + `RequireAreaAsync`），列表本身也按区域过滤，界面用 `hasAny` 不会产生「点了必被拒」的情况。

测试：`web/tests/permissions-ui.spec.ts`（用「仅 A 区 Configure」账号验证上述四类行为 + 两条路由挡回）。

## 轮询与用户操作分离（第四轮审查）

自动刷新是为了「数据新」，不是为了「让人以为在加载」。原先多处把定时轮询和用户主动刷新走同一个 `loading`，产生三种可感知的毛病：

| 位置 | 周期 | 原表现 | 现在 |
|------|------|--------|------|
| 计算页 `CalculationsView` | **2 秒** | 全表 `v-loading` 遮罩每 2 秒亮一次——遮罩会拦截指针事件，等于行几乎点不动 | 轮询不点亮遮罩（`refresh(false, true)`），保留 `!loading` 守卫避免抢占手动刷新 |
| 计算任务 `CalcJobsView` | 3 秒 | 同上 | 同上，并加 `refreshing` 防止轮询叠加 |
| 网关管理 `GatewaysView` | 5 秒 | 同上 | 同上 |
| 采集诊断弹窗 | 3 秒 | 「刷新」按钮自己每 3 秒转一圈 | 轮询不置 `busy` |
| 系统状态 `SystemView` | 10 秒 | 「刷新」按钮自己转，且**每次失败弹一条 toast**——断网时 10 秒一条连成一片 | 失败改为页内 `el-alert` 常驻提示（保留上次数据），恢复后自动消失；按钮不再自己转 |
| 报警页 `AlarmsView` | 30 秒 + 每条推送 | 每条报警推送都触发全表遮罩 + 整表重拉，报警洪峰时列表一直在闪，正好挡住确认操作 | 推送/定时刷新走 background：不遮罩；失败只在失败链首次提示，恢复后重置 |

**一个必须注意的陷阱**：给 `load()` 加 `background` 参数后，`@click="load"` 会把 **MouseEvent 当成 background 传进去**（truthy），手动刷新就再也不显示 loading。所有按钮都必须写成 `@click="load()"`。本轮已修 `SystemView`、`CollectorDiagnosticsDialog` 两处。

**另一个陷阱**：轮询改成不置 `loading` 后，若轮询会中断手动请求（`AbortController` + generation），手动请求的 `finally` 会因 generation 不匹配而跳过清理，`loading` 永久卡住。因此轮询入口保留了 `!loading.value` 守卫：手动刷新进行中，后台轮询直接跳过。

测试：`web/tests/polling-ux.spec.ts`（拦截 `/api/health` 持续 500，验证页内提示出现、按钮不转、恢复后提示消失）。

## 数据与交互语义（第五轮审查）

### 「运行时长」显示的其实是系统开机时长

`/health` 里 `uptimeSeconds = Environment.TickCount64 / 1000`——这是**机器开机时长**，服务重启不会归零。而界面拿它在两处显示「运行时长」和「启动于 {时间}」，于是：SCADA 服务重启后，页面仍显示「已运行 3 天」「启动于 3 天前」。运维据此判断「服务多久没重启」会得到完全错误的结论。

旁证：`MetricsEndpoints` 的 `scada_uptime_seconds` 用的是 `Process.GetCurrentProcess().StartTime`，同一系统里两个「uptime」口径不一致。

修法：`uptimeSeconds` 改为进程运行时长（与 metrics 对齐），另给 `hostUptimeSeconds` 表示机器开机时长；系统状态卡片并列显示「启动于 … · 主机已开机 …」，才能区分「服务刚重启」和「整机刚重启」。

测试：`web/tests/health-uptime.spec.ts`（断言 `hostUptime >= uptime` 且新起服务的 `uptimeSeconds < 30 分钟`——若退回系统开机时长，宿主机连续开机较久时即失败）。

### 单输入框表单按回车会整页刷新

`el-form` 渲染成原生 `<form>`，Element Plus **不拦 submit**。按 HTML 规范，表单没有提交按钮且「阻断隐式提交的字段」不超过 1 个时，回车会触发隐式提交 → 跳回当前 URL = **整页刷新，对话框里填的内容全丢**。

实测「重置密码」对话框：输入新密码后按回车，触发 **3 次主框架导航**。

- 多输入框表单天然安全（≥2 个 text/number/date 输入时浏览器不隐式提交），所以这个问题长期没被发现
- 受影响并已修：重置密码对话框、画面布局编辑器名称、网关归属对话框、报警暂挂对话框（均加 `@submit.prevent`）
- 重置密码是敏感操作，回车**故意不提交**，只阻止刷新
- 新增表单若只剩一个输入框，必须带 `@submit.prevent`

测试：`web/tests/form-enter.spec.ts`（输入密码按回车，断言 `framenavigated` 为 0 且对话框与输入值都在）。

**检测命令**（给未来的表单复查用）：扫描 `src` 下所有 `<el-form>`，找出没有 `@submit` 且「阻断隐式提交的字段」≤1 的表单（`el-input` 非 textarea、`el-input-number`、`el-date-picker` 各算一个）。

```
python - <<'EOF'
import re, pathlib
for p in sorted(pathlib.Path('src').rglob('*.vue')):
    t = p.read_text(encoding='utf-8')
    for m in re.finditer(r'<el-form\b([^>]*)>(.*?)</el-form>', t, re.S):
        a, inner = m.group(1), m.group(2)
        if '@submit' in a: continue
        n = sum(1 for i in re.finditer(r'<el-input\b([^>]*?)/?>', inner) if 'type="textarea"' not in i.group(1))
        n += len(re.findall(r'<el-input-number\b|<el-date-picker\b', inner))
        if n <= 1: print(f"{p}:{t[:m.start()].count(chr(10))+1} blocking={n}")
EOF
```

## 统计口径与结果披露（第六轮审查）

### 总览「未确认报警」最多只显示 10

```ts
const activeAlarms = computed(() => alarms.value.filter(x => !x.endTs).slice(0, 10))
const unackCount = computed(() => activeAlarms.value.filter(x => !x.ackTs).length)
```

先 `slice(0, 10)` 再统计——**卡片数字被硬性截断在 10**，副标题「当前活动报警 N 条」同样只算这 10 条。现场 30 条未确认报警时，首屏显示「10」，直接误导值班人员对报警负荷的判断。

修法：改取服务端 `/alarms/summary` 的全量统计（该接口最多统计 5000 条活动报警），`summary` 拉取失败时退回「已加载部分」的估算，避免显示 0。副标题用 `未确认 + 已确认 + 恢复未确认` 得出活动总数。

测试：`web/tests/overview-usability.spec.ts` 第二个用例（拦截 summary 返回 42/3/1，断言卡片显示 42、副标题 46 条）。

### 报警列表被静默截断

前后端都写死 `limit: 1000`，服务端 `Take(Math.Clamp(take,1,5000))` 直接裁掉多余部分，**界面没有任何「还有更多」的提示**。更隐蔽的是等级/关键词筛选都在客户端做——只能过滤已加载的这 1000 条，用户以为在搜全量。

修法：请求 `PAGE_LIMIT + 1`，多出来的一条用于判定截断；截断时显示常驻警示（说明筛选只作用于已加载部分、历史查询应缩短时间范围）。

测试：`web/tests/alarm-usability.spec.ts` 第二个用例（拦截实时查询返回 1001 条，断言警示出现）。

**这一类问题值得单独记住**：`limit`、`slice`、`Take` 出现在「统计」和「列表」两个语境时含义不同——统计必须用全量接口，列表必须披露截断。

## 限制

- 测点没有启用标志，故无「批量启用」。
- 测点无厂区 `areaId`（区域指寄存器区），故无「批量改厂区」。
- 工位 / 权限仍走原有区域权限；批量删除不可恢复。
- 报警页暂无「批量暂挂」：暂挂按报警规则生效，多条不同规则的报警合并暂挂语义不清，需先约定交互。

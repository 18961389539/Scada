# 诊断包

现场出问题时，先在管理端生成一个诊断包，再交给支持人员；比让对方远程连机器或手工找日志可靠得多。

## 生成

仅管理员（`Admin` 策略）：

```
POST /api/maintenance/diagnostics   立即生成并下载 diag_yyyyMMdd_HHmmss.zip
```

包同时保留在 `Scada:DiagnosticsRoot`（默认 `data/diagnostics`），最多保留 20 个，超出按修改时间删最旧。

## 包里有什么

| 文件 | 内容 |
|---|---|
| `manifest.json` | 生成时间、应用版本、机器名、操作系统与运行时、CPU 核数、进程运行时长、各表计数（设备/测点/报警规则/报警事件/用户/画面/模板/网关）、关键配置项 |
| `health.json` | 健康状态、告警列表、每台设备的在线状态与错误、总线积压与丢弃数、历史暂存积压、可用磁盘 |
| `db-check.json` | 配置库执行 `PRAGMA quick_check` 的结果；库不存在或打不开时记录原因，不中断打包 |
| `logs/log-*.txt` | 最近 3 个日志文件，总量上限 9 MB，超出则少带 |

## 不含什么

- 不包含设备行本身：OPC 密码等字段以受保护格式存在设备表里，直接导出等于把密文带走。
- 不包含用户密码哈希、令牌、网关密钥或任何配置文件原文。
- 不包含历史库：需要历史原始数据时用备份包，不用诊断包。

这三条有测试守着（`DiagnosticServiceTests.BundleNeverContainsPasswordHashesOrCredentials`），改动时不要绕过。

## 典型用法

1. 现场反馈“曲线断了/报警不响/网关掉线”，先让对方生成诊断包。
2. 看 `health.json` 的 `warnings` 与 `busDropped`：有丢弃说明写入链路跟不上，配合 `historySpool.pendingBytes` 判断是数据库慢还是磁盘满。
3. 看 `db-check.json`：不是 `ok` 说明配置库已损坏，优先走备份恢复流程。
4. 看 `manifest.counts`：设备/测点数量与现场认知不符，说明配置被改过或迁移过头。
5. 日志按时间切片定位异常段，再回到代码核对。

## 已知限制

- 诊断包是单点快照，不含历史趋势；需要时间维度时多取两次对比。
- 日志只带最近 3 个文件，滚动快的高频故障可能已经滚出窗口。
- 包内包含机器名与内部路径，对外提供前应确认接收方可信。

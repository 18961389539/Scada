# 工程管理：工程包、版本快照与回滚

入口：组态配置 → 工程管理（`/config/project`），接口前缀 `/api/project`，需要 Configure 权限。

## 工程包格式

`GET /api/project/export` 导出 JSON：`format`、`exportedTs`、`sections`。各段为 `areas`、`roles`、`devices`、`tags`、`calcJobs`、`alarmRules`、`reportTemplates`、`objectTemplates`、`screens`、`controlPoints`（控制策略，键为测点键，每个测点一条）、`controlSequences`（顺控，键为名称，`steps` 中测点写为 `tagRef`，完成条件写为 `#{测点键}`），每项为 `{ key, areas, data }`。

- 数据库自增编号不入包，引用一律改用自然键：区域、角色、设备、计算任务、报表/对象模板、画面用名称；测点用 `设备名/测点名`，无设备时为 `@测点名`；报警规则用 `测点键|规则稳定键`：稳定键为规则自身的 `key` 字段（新建时自动生成 32 位十六进制，同一测点内唯一），不随规则顺序、类型或其他规则的增删变化。
- 引用字段命名为 `xxxRef`，测点组用数组（`readTagRefs`/`writeTagRefs`）；表达式与脚本中的测点引用写为 `#{测点键}`，导入时换回目标库编号。
- 不入包：派生测点（导入后由计算任务重新生成）、对象实例、网关与通知通道（环境对象，按名称匹配，目标环境没有时置空并给出警告）、用户及其授权分配、OPC 密码、停用（OutOfService）状态、各类修订计数、运行数据。

旧格式兼容：早期包与旧快照中的报警规则没有 `key`，键为 `测点键|类型|序号`（同测点同类型内按编号排序）。导入、比较与回滚前会先升级：按同样的序号规则对应到当前库中的规则并沿用其稳定键；对应不到的给确定性的 `legacy-类型-序号`，同一个旧包重复导入结果一致。

## 导入（发布）

1. 上传文件 → `POST /import/preview`：给出每项动作（新增/覆盖/跳过/改名新增/删除）和字段级差异、校验错误、越权项，以及当前配置的内容哈希 `baseSha`。
2. 冲突（同键已存在且内容不同）默认跳过，可全局或逐项改为覆盖或改名（追加 `_导入`、`_导入2`…）。改名会级联到依赖它的键与引用。
3. `POST /import` 必须携带预览时的 `baseSha`；预览后配置被他人修改则返回 409，需重新预览。
4. 应用在一个事务内按依赖顺序执行，沿用各实体原有校验（表达式、循环依赖、脚本白名单等）。任一项失败或越权：整体回滚，返回 400/403，并记失败/拒绝审计。
5. 成功后：若当前配置与最近快照不同先存 `pre-import` 快照，再存 `import` 快照；写一条 `Project` 操作日志，含全部差分。

预览本身就是在事务中真实执行后回滚，因此预览与发布的校验结果一致。项目操作在进程内串行执行。

### 预览没有事务外副作用

逐项核查了 `ProjectApplier` 的执行路径：它只拿到 `ConfigDbContext` 和纯校验服务（计算定义校验、表达式编译、报表列校验），所有写入（含关闭被删计算输出的活动报警事件、`ExecuteUpdate`）都在同一事务内，随回滚撤销。运行时动作集中在 `ProjectService.PublishRuntimeAsync`，只在事务提交后调用：重载配置快照与采集（同时让授权模型失效，实时推送随之刷新）、让计算引擎重载；网关按已提交配置拉取，没有主动下发。审计与快照记录也在事务内。预览中的越权和校验错误只在结果中返回，不写拒绝/失败审计（正式发布才写）。测试 `PreviewsHaveNoRuntimeOrOutOfTransactionSideEffects` 断言导入预览、越权预览、回滚预览前后：配置重载次数、计算引擎重载请求、授权模型代数、运行时配置版本、审计条数、快照条数、未结束报警事件和工程内容哈希全部不变。

### 不入包的运行状态与冲突哈希

现场控制的挂牌（禁止操作/检修中）、就地/远程控制权、待复核请求和顺控运行记录不入包，也不进快照。理由：挂牌和控制权表达的是**此刻现场的安全状态**（谁在检修、哪台设备被现场接管），由运行人员按现场情况挂摘，并有完整的挂摘记录。若跟随工程包导入或回滚，回滚到旧版本会把正在检修的设备“摘牌”、或把旧环境的牌带到新现场，直接造成误操作风险。因此导入与回滚从不修改这些表；测试 `ControlPointsAndSequencesAreInProjectPackageAndRollBack` 验证回滚后挂牌仍在。正在运行的顺控不能被导入或回滚修改或删除（应用时报错）。

报警规则停用状态/原因、设备停用时间、OPC 密码不入包，也不入 `baseSha`。理由：它们由运行人员随时修改，与工程设计无关；导入与回滚在应用时总是读取并保留库里的当前值，而不是用包里的值覆盖，因此预览后这些字段被改不会造成丢失更新，没有必要让它们把发布变成 409。测试 `ExcludedOperationalStateIsPreservedAcrossPreviewAndPublish` 覆盖：预览后停用规则，发布成功且停用状态保留。

## 版本快照与回滚

- 种类：`manual`（手动）、`import`/`pre-import`、`rollback`/`pre-rollback`、`screen-publish`（画面发布后自动）。快照为完整工程包，记录内容哈希、作者、时间和摘要。
- 比较：`GET /diff?from=<id|current>&to=<id|current>`，任意两版本。
- 回滚：`POST /versions/{id}/rollback/preview` 给出影响（包括将删除的对象），确认后 `POST /versions/{id}/rollback {baseSha}`。回滚是镜像应用：目标版本没有的对象会被删除。被对象实例绑定的设备或画面拒绝删除，整体回滚失败。
- 下载快照原文需全局 Configure。
- 画面发布后的自动快照在发布提交之后执行，失败不撤销发布，但会：记错误日志；`/health` 出现 `config_snapshot_failed` 告警（状态 degraded），直到下一次快照成功；发布结果返回 `warning`，设计器以警告提示。

## 工作流选择：离线编辑后发布

选择“离线编辑 + 导入即发布”，不做逐对象草稿/发布：

- 运行时采集、计算、报警直接读取配置实体，草稿态需要为每类实体维护双份模型并改造所有运行组件，侵入大、风险高；
- 工程包 + 预览 + 原子应用 + 自动前后快照已覆盖“先改后审、一次生效、可回退”的核心诉求，且同一机制也用于跨环境迁移；
- 画面已有自身的草稿/发布，发布时自动快照，纳入同一版本线。

代价：在线页面的直接修改即时生效，不经草稿；多人并发只做预览后变更检测（409），不做合并。

## 权限与审计

- 导出与预览/比较结果按区域可见性过滤，返回隐藏条数；区域内对象需对应区域 Configure，全局对象（区域、角色、模板、画面、无区域测点等）需全局 Configure。计算任务写测点另需 Control。
- 导出、快照、导入、回滚均写审计；拒绝和失败也记录。

## 已知限制

- 无区域的计算测点需要全局权限才能导入。
- 包格式只有当前版本，未来格式变更需要迁移器；大工程包性能未实测。

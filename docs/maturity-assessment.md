# SCADA 成熟度与功能差距（2026-10-24）

## 评估对象与结论

用户指定的本地 `main` 为 `936d189`。它提供 Modbus TCP 采集、实时监视、基础控制、报警、历史趋势、日/月统计、三种角色和配置库备份，属于初版监控系统，尚未达到可独立承担生产运行的成熟 SCADA 水平。本次未重新构建或运行 `main`，对它的判断来自代码检查。

当前工作位于 `codex/scada-capabilities`。该分支已增加可视化组态、设备对象模板、Modbus RTU、S7、OPC UA 接入、证书与变量浏览导入、采集诊断，以及独立网关采集、补传、远程命令/回执、工程操作和网关管理页面，并补充历史持久暂存、完整备份恢复、会话撤销、容量告警和诊断包。它处于具备工程化雏形的功能验证阶段；相关功能尚未合并到本地 `main`。完整产品成熟度不能用页面数量或自动测试通过率代替。

## 生产验收优先项

1. **历史数据可靠性。** 写库失败已改为追加到 `data/history/_spool/history-spool.ndjson` 并按序补传，补传成功才删除（`HistorySpool`，上限 16MB，超限计数拒绝），进程重启后自动续传；`RealtimeBus` 满队列不再静默挤掉旧数据，改为拒收并累计 `DroppedTotal`，`/health` 暴露 `busDropped` 与 `historySpool` 积压。剩余缺口：暂存写满后的降级策略只做到"计数+记日志"，尚未做磁盘写入前的容量预警与分段轮转；断电、满盘、慢盘下的验收仍未做。
2. **控制执行闭环。** 当前同一测点的写后回读不能证明电机、阀门等设备已经实际动作。远程命令已增加编号去重、执行授权、未知状态查询和持久回执；本地控制仍需补齐这些状态。设备许可、执行状态和独立反馈仍须建模，并与现场 PLC 约定验收边界。
3. **权限和审计闭环。** 三种全局角色不能表达“只允许操作某车间某设备”。登录已具备失败限速与锁定（同一用户名+来源 5 次/5 分钟），已知账号的失败尝试写入操作日志；管理员改角色、停用或改密后，已建立的实时连接会被立即断开，另有 15 秒周期兜底。仍需：资源级授权贯通 HTTP、SignalR、画面动作和后台任务，以及配置前后差异和失败操作的完整审计。
4. **完整恢复。** 已提供完整备份包：配置库、历史库、历史暂存、Data Protection 密钥、OPC PKI 与应用版本写入同一 zip，附 SHA256 清单并可用 `verify` 逐文件核对与数量校验；管理员可通过 `/api/maintenance/backups` 生成、校验、下载，停机窗口用 `tools/Scada.BackupTool` 离线还原。已在隔离目录完成端到端演练（源实例备份 → 离线还原 → 从还原数据启动，设备/测点/规则与登录均一致），记录见 `backup-restore.md`。仍缺：真实体量历史库的备份耗时与磁盘规划、异地副本策略；Windows DPAPI 对服务账户及主机的绑定必须在换机时重新录入凭据，备份无法规避。
5. **现场与长稳证据。** 测试点数是规划目标，不是已验证容量。需记录设备数、点数、变化率、轮询周期、客户端数、CPU/内存/磁盘、采集延迟和数据完整率，覆盖断网、重启、慢数据库、满盘及证书到期等场景。

功能推进顺序见 `product-roadmap.md`。第 3 项管理页面已通过本地验收，完整安装运行和现场验收仍待完成。第 4、5、7、9、10 项主体待实施；第 6、8、11 项已有可靠性、会话和运维增量，但不能据此标记完整范围完成。

## 本轮可靠性加固（2026-10-24）

- **网关持久队列并发写。** `GatewayAgentStore` 原先每个实例各自 `BEGIN IMMEDIATE` 抢写锁、无重试，并发写入稳定抛 `SQLite Error 8: 'attempt to write a readonly database'`。现改为按数据库文件在进程内串行（静态写门），并在 BUSY/LOCKED/READONLY 上做退避重试；跨进程争用由 `busy_timeout=5000` 兜底。
- **历史写入不再静默丢数。** 写库失败先落盘暂存，恢复后按原序补传；总线满队列改为拒收并计数，而不是挤掉已排队数据。
- **可观测性。** `/health` 增加 `busDropped`、`historySpool.pendingBytes/spilledBatches/rejectedBatches`。
- **持续集成。** 新增 `.github/workflows/ci.yml`：后端还原/构建/全量测试（含 trx 上传）与前端 `npm run build` 类型检查+构建，push 到 `main`、PR 及手动触发。
- **登录与会话。** 登录失败按“用户名 + 来源地址”限速，5 次/5 分钟窗口后锁定 5 分钟并返回 429 + `Retry-After`；已知账号的失败尝试与成功登录写入 `OperationLog`，未知用户名只记服务端日志，避免审计表被刷量。`SessionRegistry` 登记每条实时连接的身份快照，管理员改角色、停用、改密、删号时立即断开该用户的连接，`SessionReaper` 每 15 秒兜底回收直接改库造成的失效会话。
- **完整备份。** `BackupService` 生成含配置库、历史库、历史暂存、Data Protection 密钥、OPC PKI 与 SHA256 清单的 zip，配置库与历史库均用 SQLite 在线备份复制而非直接拷贝；`verify` 逐文件核对大小/哈希并校验设备、测点、规则数量；过期包按 `BackupRetentionDays` 自动清理。默认每周自动生成（`FullBackupIntervalHours`，0 关闭），停机窗口用 `tools/Scada.BackupTool` 离线还原。恢复流程见 `backup-restore.md`。
- **容量告警。** `SystemWatch` 每 30 秒评估可用磁盘、历史暂存积压与实时总线积压，超阈值时 `/health` 转 `degraded` 并返回 `warnings[]`（首次请求即计算，不必等首个周期）；总线丢弃按“本次新增”告警，避免一次抖动让状态永久停在 degraded。
- **端到端入 CI。** `.github/workflows/ci.yml` 增加 `e2e` 作业（windows-latest，`continue-on-error`），因浏览器场景依赖真实 Edge 与 OPC 模拟器，先作观察项不阻断合并。
- **诊断包。** `POST /api/maintenance/diagnostics` 生成 zip：版本与配置规模、健康快照（设备状态、总线积压与丢弃、暂存积压、磁盘）、配置库 `PRAGMA quick_check`、最近 3 个日志文件（上限 9MB）。只含计数与状态，不含设备行、口令哈希或密钥，由测试守住。说明见 `diagnostics.md`。

## 网关迁移用例的历史竞态与后续处理

`web/tests/gateway-management.spec.ts` 的「设备迁移需等待网关确认停用」用例不稳定：本轮单跑 6 次 3 过 3 败，`--repeat-each` 模式下 4/4 失败。已定位到服务端判定链，但没能构造出稳定的“等网关确认”状态。

- 失败证据：`GET /api/gateways/assignments/{id}` 在 20 秒内始终返回 `{"enabled":false,"canMove":true,"blockReason":null}`，即网关已确认停用配置。
- 用例原本靠代理对 `/api/gateway-agent/configuration` 返回 304 来阻止网关拿到新配置（`holdConfiguration`）。实测该拦截没有生效：失败时把代理收到的全部请求 URL 打到标准输出，日志中没有任何配置请求记录，说明拦截点没覆盖实际请求路径。
- 追加尝试也未奏效：先轮询 `blockReason` 再断言界面（仍 20 秒拿不到期望值）；改为对配置接口一律挂起（带条件 304、不带条件 503）后 `--repeat-each=3` 仍 2 败。相关实验改动已全部回退，未留在文件里。

建议按下面任一方向处理，均需在网关管理改动定稿后进行：

1. 把“迁移门禁”的验证下移到服务端测试，直接构造 `gateway.LastSeenTs < device.DisabledSinceTs` 与已确认/未确认两种配置快照，断言 `AssignmentBlockAsync` 的返回。
2. 浏览器用例只断言可观察行为——「保存采集位置」按钮禁用、最终 `canMove` 变为 true——不绑定具体提示文案，避免依赖无法稳定构造的中间态。
3. 若要保留端到端门禁验证，先用日志确认真实配置请求路径（含方法、URL、条件头），再修正代理的拦截条件。

以上为此前实测与实验记录。后续重新读取代码时保留这些证据，并将代理匹配改为 URI pathname，停用前必须观测到至少一次实际拦截的配置轮询；该同步条件也排除了开关设置前仍在途的配置请求。保留有界请求路径与进程退出诊断，失败附件不含认证头或密钥。修正后迁移用例连续 4 轮通过，随后全量 34 项通过。没有以固定等待、放宽迁移门禁或跳过断言处理此问题；早先网关退出与队列恢复超时的独立记录仍按 `remote-gateway.md` 跟踪。

对照采用成熟 SCADA 常见的工程化能力，不将所有厂商、模块或授权档位视为相同配置：

- Ignition 的 [Store and Forward](https://www.docs.inductiveautomation.com/docs/8.3/platform/store-and-forward) 提供内存/磁盘缓存、失败重试及有序转发，可作为历史可靠性对照。
- [报警管理](https://docs.inductiveautomation.com/docs/8.3/platform/alarming) 与 [报警通知管线](https://www.docs.inductiveautomation.com/docs/8.3/ignition-modules/alarm-notification/alarm-notification-pipelines) 包含暂挂、备注、通知路由和升级；[值班名单](https://www.docs.inductiveautomation.com/docs/8.3/ignition-modules/alarm-notification/on-call-rosters) 联动用户排班。
- [冗余机制](https://www.docs.inductiveautomation.com/docs/8.3/platform/ignition-redundancy) 包含主备角色、配置同步及故障切换，可作为第 11 项验收参照。

这些资料说明对照能力，当前产品是否具备该能力仍以本仓库代码及实际验收结果为准。
